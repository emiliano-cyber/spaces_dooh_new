     # en que estado esta su base, sin tocar nada
     /opt/space-os/update.sh --dry-run

     # y si quieres el detalle de migraciones:
     tail -n 40 /var/log/space-os/update.log

 QUE ESPERAR DE --dry-run:

     "sin cambios"                          -> al dia
     "pull v0.4.2 -> 3 migraciones pendientes" -> hay actualizacion esperando
     cualquier mencion a "BACKUP VACIO"     -> PARA. Avisa. No sigas.

 LO IMPORTANTE, Y ES LO QUE MAS FACIL SE OLVIDA:

 Una instancia NO se actualiza aplicandole migraciones a mano. Se actualiza
 sola, jalando la imagen nueva del registry. La cadena es:

     1. el PR aterriza en main
     2. sale una version nueva al canal (release.yml)
     3. la instancia la jala en su cron de las 04:17

 Si alguna vez te ves corriendo migrar.mjs a mano contra un servidor, algo
 se salto un paso.

 6 · LA TRAMPA QUE COSTO EL DIAGNOSTICO DE HOY
-------------------------------------------------------------------------------

 Si migrar.mjs sale con CODIGO 3 diciendo que una migracion ya aplicada
 cambio de contenido: casi seguro NO cambio. Lo que cambio es el arbol de
 trabajo, que quedo en CRLF.

 git status NO puede delatarlo: con el atributo "text" de .gitattributes,
 git normaliza al commitear y el arbol sale limpio igual.

 COMO SE VE (desde Git Bash, en la raiz del repo):

     for f in db/migrations/*.sql; do
       [ "$(sha256sum < "$f")" != "$(tr -d '\r' < "$f" | sha256sum)" ] && echo "CRLF: $f"
     done

     Sin salida = el arbol esta bien.

 COMO SE ARREGLA (con git status limpio comprobado ANTES, o se lleva por
 delante una migracion sin commitear):

     git status --short db/migrations/     # tiene que salir VACIO
     rm -f db/migrations/*.sql && git checkout -- db/migrations/

 NO USES --forzar-checksum PARA ESTO. Esa bandera le dice al registro que
 el contenido nuevo es el bueno, y aqui el bueno era el viejo: grabaria la
 mentira.

 Esta escrito completo en CLAUDE.md, en el bloque de trampas de entorno.
