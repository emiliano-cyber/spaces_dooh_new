QUE HACE
  Hasta hoy el panel sabe si una instancia contesta y en que version se quedo.
  No sabe si su ultima ACTUALIZACION fue bien. Con esto, cada instancia manda
  el codigo de salida de su `update.sh`, y el panel lo traduce a una frase.

  La diferencia que compra: una instancia que fallo la migracion a medias
  (codigo 2, «LA BASE PUDO CAMBIAR») y otra que no aplico nada (codigo 3) hoy se
  ven IGUAL en el panel -- las dos como «rezagada». La primera necesita que
  alguien entre esta noche; la segunda puede esperar.

QUE NO HACE
  No aplica ninguna migracion. No cambia la imagen de ninguna instancia. No
  toca ninguna base. No cambia nada que vea un cliente.

--------------------------------------------------------------------------------
 ⚠️ EL ORDEN NO ES NEGOCIABLE: PRIMERO EL PADRE, DESPUES LAS INSTANCIAS
--------------------------------------------------------------------------------
  El receptor del PADRE rechaza un reporte ENTERO si trae una clave que no
  conoce -- a proposito, y por eso el panel no acumula datos del negocio de
  nadie. `codigo` es una clave nueva.

  Consecuencia: si una instancia empieza a mandar `codigo` ANTES de que el
  PADRE aprenda a aceptarlo, el PADRE le rechaza el reporte completo y esa
  instancia se queda MUDA en el panel -- sin version, sin fecha, sin nada --
  precisamente en la corrida en que algo pudo fallar.

  Al reves no pasa nada: el PADRE trata `codigo` como OPCIONAL, asi que una
  instancia con el `update.sh` viejo sigue reportando exactamente como hoy.

  PRIMERO A (el padre), DESPUES B (DEMO), DESPUES C (g500). Sin saltarse A.

 A2 · Traer el codigo

--------------------------------------------------------------------------------
 A3 · 🚦 GATE · que el receptor ACEPTE un reporte con `codigo`
--------------------------------------------------------------------------------
  Esto no toca el servicio ni el disco: solo le pregunta al validador que dice
  de tres cuerpos. Es la comprobacion que autoriza el paso B.

cd /var/www/Spaces/apps/flota
node -e '
import("./reporte.mjs").then(({ validarReporte }) => {
  const base = { ok: true, version: "v0.5.0", ultimaMigracion: null,
                 base: "ok", canal: "estable", uptime: 120, instancia: "demo" };
  console.log("sin codigo (update.sh viejo):", validarReporte(base).ok);
  console.log("con codigo 2:               ", validarReporte({ ...base, codigo: 2 }).ok);
  console.log("con una clave inventada:    ", validarReporte({ ...base, traza: "x" }).ok);
});
'

  ESPERADO, las tres lineas y en este orden:

    sin codigo (update.sh viejo): true
    con codigo 2:                 true
    con una clave inventada:      false

  🚦 Si la segunda dice `false`, el codigo nuevo no esta cargado: vuelve a A2.
  🚦 Si la tercera dice `true`, PARAR y avisar: el receptor dejo de rechazar
     claves que nadie declaro, y ese guard es lo que impide que datos del
     negocio de un cliente acaben en el disco del padre.

systemctl restart <el-servicio-que-salio>
systemctl status  <el-servicio-que-salio> --no-pager | head -12

  ESPERADO: `active (running)`.

  Si en A esta tambien el receptor de reportes como servicio aparte, sale en la
  misma lista. Reinicia los dos.

 B2 · 🚦 GATE · correrlo CON SU CONFIGURACION
--------------------------------------------------------------------------------
  El `SPACE_OS_CONF` NO es opcional. Sin el, este guion actualiza otra cosa.

SPACE_OS_CONF=/etc/space-os/demo-instancia.env /opt/space-os/update.sh; echo "codigo de salida: $?"

  ESPERADO: lo de siempre -- normalmente `sin cambios` -- y `codigo de salida: 0`.
  Si sale otro codigo, ANOTALO y sigue: el resto de la tarjeta sirve igual, y de
  hecho ese codigo es lo que estamos aqui para ver en el panel.

  🚦 Si dice que no encuentra `respaldo.sh`, el `install` de B1 se llevo el
     guion pero no su vecino. PARAR y avisar.

--------------------------------------------------------------------------------
 B3 · 🚦 GATE · que el reporte haya llegado con `codigo` dentro
--------------------------------------------------------------------------------
  El archivo que el receptor acaba de escribir. La ruta puede ser otra en esta
  maquina, asi que se BUSCA en vez de recordarla:

find /var/www/Spaces/apps/flota /var/lib/space-os -name 'demo.json' 2>/dev/null

  Con la que salga:

  ESPERADO: un JSON con `"codigo":` dentro y el numero que imprimio B2.

  🚦 Si el archivo NO tiene `codigo`, mira el log de la corrida:

grep -i flota /var/log/space-os/update.log | tail -5

     · «reporte de flota OK» y aun asi sin `codigo`  -> el `update.sh` nuevo no
       se cargo: repite B1 y compara las sumas.
     · «reporte de flota NO ENTREGADO»               -> el PADRE lo rechazo.
       PARAR y NO seguir al paso C: eso es exactamente el fallo que el orden de
       esta tarjeta evita, y en C se repetiria contra una instancia de cliente.

 ⛔ LO DE ABAJO NO ES EL PASO SIGUIENTE
================================================================================
  Es la VUELTA ATRAS, y va comentada a proposito. No la corras si los pasos de
  arriba salieron bien: esto deshace el trabajo. Ya paso en este proyecto que
  una tarjeta puso un comando destructivo en la fila y se ejecuto por inercia.

  Cada parte se deshace por separado, y en el orden CONTRARIO al de arriba:
  primero las instancias, el PADRE al final. Si se quitara el PADRE primero,
  las instancias que aun mandan `codigo` se quedarian mudas.

  · g500 y DEMO -- volver a su `update.sh` de antes:

# cp -a /opt/space-os/update.sh.antes-fase2 /opt/space-os/update.sh

  · El PADRE -- volver al commit anterior. `<commit-anterior>` es el hash que
    imprimio el PRIMER `git log` de A2:

# cd /var/www/Spaces && git checkout <commit-anterior> && systemctl restart <el-servicio>

  Y lo que NO hace falta deshacer: los `estado/*.json` que ya se escribieron con
  `codigo` dentro. El panel viejo ignora la clave; no molesta.
