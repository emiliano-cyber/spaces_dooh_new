##############################################################
#  12 · INSTALAR EL RESPALDO DIARIO EN UNA INSTANCIA
#  Levantada el 2026-09-22. NO EJECUTADA todavia.
#  La corre UNA PERSONA. Claude no entra a ningun servidor.
##############################################################
#
#  QUE PASA HOY
#  ------------
#  g500 -la unica instancia con datos reales de cliente- saca
#  sus datos del droplet UNICAMENTE cuando se despliega una
#  version nueva. No es un olvido de configuracion: es donde
#  vive el dump. `update.sh` respalda en su paso 3 y a ese paso
#  solo se llega si hay imagen nueva; las corridas "sin cambios"
#  salen antes.
#
#  Como `estable` no se mueve desde el 17/09, la copia remota
#  mas reciente tiene CINCO DIAS y la subio una persona a mano.
#  Medido en docs/evidencias/11-g500-sin-respaldo-programado.md
#
#  La regla real era "la frecuencia de tus respaldos la decide
#  el ritmo de los releases". Esta tarjeta la rompe.
#
#  QUE INSTALA
#  -----------
#  `respaldo-diario.sh` + `conexion-pg.sh` en /opt/space-os/, y
#  una linea de cron. NO toca `update.sh`, NO toca la base y NO
#  reinicia nada. Si algo sale mal, la vuelta atras es borrar la
#  linea de cron: la instancia queda EXACTAMENTE como hoy.
#
#  DECISION DEL DUENO (22/09): el respaldo diario es de TODAS
#  las instancias, no solo de las que tienen datos reales.
#  Por eso hay DOS bloques: los montajes no son iguales.
#
##############################################################
#  LA HORA, Y POR QUE ESA
##############################################################
#
#    03:41  respaldo diario   <- esta tarjeta
#    04:17  update.sh         <- ya existente, no se toca
#
#  Va ANTES del update, y con 36 minutos de margen, por tres
#  motivos:
#
#   1) Si el update de las 4:17 sale malo, hay un respaldo
#      independiente de hace media hora. (El propio update hace
#      el suyo, pero ese es justo el que no existe si el update
#      no llega a correr.)
#   2) No se solapan. El dump de una base de ~6 MB tarda
#      segundos, pero el margen es gratis.
#   3) El minuto 41 no es redondo a proposito: los minutos 00,
#      15, 30 y 45 son donde se amontonan los cron de todo el
#      mundo, y el `--comprobar` de `update.sh` ya corre cada
#      15 minutos en punto.
#
##############################################################
#  ⚠️  ANTES DE EMPEZAR, LOS DOS ERRORES QUE YA COSTARON TIEMPO
##############################################################
#
#  1) LA REGION NO ES `nyc3`. `respaldo.sh:95` la trae como
#     valor por omision y ESTA CUENTA USA `sfo3`. Si la
#     instancia ya tiene SPACES_REGION en su instancia.env,
#     no hay nada que hacer: este guion lee el mismo archivo.
#     (Aprendido en la tarjeta 10.)
#
#  2) `respaldo-diario.sh` NECESITA `conexion-pg.sh` AL LADO.
#     Sin el sale con 1 y no respalda nada. Son DOS archivos,
#     no uno. `update.sh` tiene la misma relacion con
#     `respaldo.sh` y ya mordio una vez.
#
##############################################################

  install -o root -g root -m 750 /tmp/conexion-pg.sh     /opt/space-os/conexion-pg.sh &&

#       update.sh  respaldo.sh  respaldo-diario.sh  conexion-pg.sh

# --- A2 · LA PRUEBA DE VERDAD, A MANO Y ANTES DEL CRON ------
#     >>> ESTE PASO NO SE SALTA. <<<
#     Correrlo a mano es lo unico que demuestra que en ESTA
#     maquina funciona. Instalar el cron primero significa
#     enterarse del fallo dentro de 24 horas, o nunca.

ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> '/opt/space-os/respaldo-diario.sh; echo "CODIGO: $?"'

#     SE ESPERA, en este orden:
#       1 · respaldo diario -> /var/lib/space-os/respaldos/spaces_AAAAMMDD_HHMMSS.dump · base=127.0.0.1:5432/spaces
#          respaldo de NNNNNNN bytes          <- NO cero. Si dice 0 algo va mal.
#          respaldo remoto -> s3://space-os-respaldos/g500/AAAA-MM-DD-HHMM.dump (por s3cmd)
#          respaldo remoto OK: s3://...
#          respaldo diario OK: la copia de hoy salio del droplet.
#       CODIGO: 0
#
#     SI DA CODIGO 4 ("BACKUP VACIO"): no se subio nada y no se
#       toco nada. Mira el `base=` de la primera linea: si esa
#       no es la base de g500, lo que fallo fue interpretar
#       DATABASE_URL, no el respaldo.
#     SI DA CODIGO 5 ("RESPALDO REMOTO FALLIDO"): el dump esta
#       bien y SIGUE en el droplet. Si el motivo es un 403, es
#       permiso de la llave sobre ese bucket y se arregla en el
#       panel de DigitalOcean, no aqui.
#     SI DA CODIGO 1: falta un archivo o DATABASE_URL. El
#       mensaje dice cual. No se toco nada.

# --- A2b · LOS PERMISOS DEL DUMP ----------------------------
#     >>> ESTA COMPROBACION SOLO SE PUEDE HACER AQUI. <<<
#     En la maquina de desarrollo (Git Bash sobre Windows)
#     `umask` y `chmod` NO se reflejan: una prueba de permisos
#     alli da verde pase lo que pase. Medido el 22/09. Asi que
#     el arnes solo comprueba que las lineas existen, y la
#     comprobacion de verdad es esta.
#
#     Por que importa: un dump es la base ENTERA -- sin RLS,
#     sin tenant y sin sesion. Con el umask 022 de root nacia
#     en 0644, legible por CUALQUIER usuario local del droplet,
#     incluido el que corre la aplicacion.

ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> '
  ls -ld /var/lib/space-os/respaldos
  ls -l  /var/lib/space-os/respaldos | tail -4'

#     SE ESPERA:
#       drwx------  ... /var/lib/space-os/respaldos      <- 700
#       -rw-------  ... spaces_AAAAMMDD_HHMMSS.dump      <- 600
#
#     SI SALE `drwxr-xr-x` EN EL DIRECTORIO, O EL DUMP DE HOY
#     SALE `-rw-r--r--`:  >>> PARA. <<<
#       El `chmod` no corrio. No sigas al cron: cada noche
#       dejaria la base entera de un cliente legible por
#       cualquier usuario local del droplet, y encima con la
#       tarjeta diciendo que estaba arreglado.
#       Mira el log de la corrida: el guion escribe
#       "AVISO: no se pudo dejar ... en 0700" o "... en 0600"
#       cuando el chmod falla. Si NO hay AVISO y los permisos
#       igualmente estan mal, es que se instalo un
#       respaldo-diario.sh viejo -- comprueba el A1.
#
#     >>> Y NO TE FIES DEL ARNES PARA ESTO. <<<
#     Su escenario R10 es un `grep` de cuatro literales dentro
#     del guion: comprueba que las lineas ESTAN ESCRITAS, no
#     que el `chmod` llegara a correr ni que surtiera efecto.
#     Sobrevive a un renombrado de variable. Cuenta como cuatro
#     comprobaciones verdes del arnes y NO sustituye a este
#     paso. La unica comprobacion real de permisos es esta,
#     contra el droplet.

# --- A2c · ARREGLAR LOS DUMPS QUE YA EXISTEN ----------------
#     >>> ESTE PASO NO ES OPCIONAL. <<<
#     Este guion arregla el directorio y LOS DUMPS QUE EL CREA.
#     Los que ya estan ahi los dejo `update.sh`, que no se toca
#     en esta tarjeta y sigue creandolos 0644. En g500 esos
#     archivos son LA BASE ENTERA DE UN CLIENTE en -rw-r--r--,
#     y seguiran asi hasta que alguien corra esta linea.

ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> '
  chmod 600 /var/lib/space-os/respaldos/*.dump
  ls -l /var/lib/space-os/respaldos/'

#     SE ESPERA: TODOS en -rw-------, no solo el de hoy.

# --- A3 · Comprobar que el objeto EXISTE en el bucket -------
#     El log diciendo OK no es la prueba; el objeto lo es.

ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> '
  set -a; . /etc/space-os/instancia.env; set +a
  # SIN valor por omision, a proposito. La primera version de esta
  # tarjeta ponia "${SPACES_REGION:-nyc3}" y se contradecia con su
  # PROPIO aviso de arriba: ESTA CUENTA USA sfo3. Con nyc3 la
  # consulta va al endpoint equivocado y contesta 404 NoSuchBucket
  # -- que se lee como "el bucket no existe" y manda a crear uno
  # que YA EXISTE. Si la variable falta, mejor que se queje a que
  # mienta.
  : "${SPACES_REGION:?falta SPACES_REGION en /etc/space-os/instancia.env: leela en la URL del bucket, en el panel}"
  conf=$(mktemp); chmod 600 "$conf"
  printf "[default]\naccess_key = %s\nsecret_key = %s\nhost_base = %s.digitaloceanspaces.com\nhost_bucket = %%(bucket)s.%s.digitaloceanspaces.com\nuse_https = True\nsignature_v2 = False\n" \
    "$SPACES_KEY" "$SPACES_SECRET" "$SPACES_REGION" "$SPACES_REGION" >"$conf"
  s3cmd --config="$conf" ls s3://${SPACES_BUCKET:-space-os-respaldos}/${INSTANCIA:-g500}/ | tail -5
  rm -f "$conf"'

#     SE ESPERA: una linea NUEVA, con la fecha y hora de hoy y
#     un tamano de varios MB. Si el tamano es 0, PARA: el guard
#     deberia haberlo impedido y hay algo que entender.

# --- A4 · Instalar el cron ----------------------------------
#     Archivo APARTE de /etc/cron.d/space-os-update, que NO se
#     toca: asi la vuelta atras es borrar un archivo y el
#     actualizador no se entera de nada.

ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> 'cat >/etc/cron.d/space-os-respaldo <<CRON
# El respaldo sale del droplet TODOS LOS DIAS, haya o no version nueva.
# Ver vault/06-Operacion/respaldo-diario.md
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
41 3 * * * root /opt/space-os/respaldo-diario.sh >> /var/log/space-os/cron.log 2>&1
CRON
chmod 644 /etc/cron.d/space-os-respaldo
cat /etc/cron.d/space-os-respaldo'

#     OJO: el archivo TIENE que acabar en salto de linea y NO
#     puede tener punto en el nombre -- cron ignora en silencio
#     los archivos de /etc/cron.d con un punto en el nombre.
#     Por eso se llama `space-os-respaldo` y no `space-os-respaldo.cron`.

# --- A5 · Comprobar al dia siguiente ------------------------
ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> '
  tail -n 20 /var/log/space-os/respaldo-diario.log
  echo "--- veces que salio del droplet ---"
  grep -c "respaldo remoto OK" /var/log/space-os/respaldo-diario.log'

#     SE ESPERA: al menos 1, y una linea de las 03:41.
#     Hoy ese mismo grep sobre update.log en g500 devuelve 0.

# --- A6 · VUELTA ATRAS --------------------------------------
#     Deja la instancia exactamente como estaba. No hay estado
#     que deshacer: los dumps que haya creado son archivos de
#     mas, y la poda los retira sola.

ssh -i ~/.ssh/spaces_deploy root@<IP-DE-G500> '
  rm -f /etc/cron.d/space-os-respaldo
  rm -f /opt/space-os/respaldo-diario.sh /opt/space-os/conexion-pg.sh
  ls /opt/space-os/'

#  `SPACE_OS_CONF` dice QUE BASE respaldar. NO dice DONDE

#    DIR_RESPALDOS  <- $SPACE_OS_DIR_ESTADO/respaldos
#    SPACE_OS_DIR_ESTADO  <- /var/lib/space-os   (por omision)
#
#  Y NADA fija SPACE_OS_DIR_ESTADO en produccion: solo aparece
#  en los arneses. O sea que en el PADRE, si no se dice otra
#  cosa, DEMO Y EL PROPIO PADRE COMPARTEN
#  /var/lib/space-os/respaldos.
#
#  Que pasa entonces, y no es hipotetico:
#
#    · la poda deja los 3 mas recientes POR FECHA DE ARCHIVO,
#      mire de que base sea cada uno;
#    · un respaldo diario de DEMO se come ese directorio EN
#      TRES DIAS, incluido el respaldo que `update.sh` del
#      PADRE hizo ANTES DE MIGRAR -- que es justo el que da la
#      vuelta atras de un release malo;
#    · y como DEMO no tiene respaldo remoto, lo que se poda
#      NO ESTA EN NINGUNA OTRA PARTE.
#
#  Agravante: los dos escriben `spaces_<fecha>.dump`, asi que
#  MIRANDO EL NOMBRE NO SE DISTINGUE de que base es cada uno.
#  No hay forma de darse cuenta despues.
#
#  POR ESO los pasos B2 y B3 llevan `SPACE_OS_DIR_ESTADO`
#  ademas de `SPACE_OS_CONF`. **Las dos variables, siempre
#  juntas.** Si copias solo una, copiaste la que no protege.
#
