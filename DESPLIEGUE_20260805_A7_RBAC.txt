  !! OJO CON ESTO — el rollback de codigo NO es del todo limpio !!

  La migracion BORRA la columna tenants.cambios_password_hash, y el codigo viejo
  la lee en `hashDelTenant()`. Esa funcion la usa `exigirDesbloqueo()`, que a su
  vez cuelga de `exigirCambioSensible()` — o sea, de OCHO rutas:

     facturar campaña · pagar cobranza · pagar renta · crear contrato ·
     editar contrato · cancelar contrato · renovar contrato · editar arrendador

  Con el codigo viejo y la columna ausente, esas ocho devuelven 500. No es "una
  ruta que no se toca": es el cierre de facturacion y todo el flujo de contratos.

  Asi que si haces rollback de codigo, RESTAURA TAMBIEN LA BASE:

    zcat ~/backups/<el backup del paso 1>.sql.gz | sudo -u postgres psql -d spaces_prod

  Alternativa mas rapida si no quieres perder los datos creados desde el backup:
  devolver solo la columna, vacia. Deja el control de cambios apagado, que es
  como esta hoy, y las ocho rutas vuelven a funcionar:

    sudo -u postgres psql -d spaces_prod -c "alter table tenants add column if not exists cambios_password_hash text;"

REVERTIR SOLO EL PERMISO DE INVENTARIO (si estorba a ventas y no quieres
desplegar): devolver la escritura del catalogo a COMERCIAL es una fila.

  sudo -u postgres psql -d spaces_prod -c "insert into rol_permisos (rol,modulo,accion) values ('COMERCIAL','inventario','crear') on conflict do nothing;"

  Eso le devuelve a COMERCIAL el alta y edicion de pantallas sin tocar codigo.
